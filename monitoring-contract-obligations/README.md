# Мониторинг исполнения договорных обязательств

Проект веб-системы для загрузки договоров, извлечения обязательств и
контроля их исполнения.

## Архитектура MVP и production-переход

Приложение построено как модульный монолит с отдельным процессом обработки
документов:

```text
Browser -> HTTP API/auth middleware -> domain registry -> PostgreSQL
Document upload -> document_processing_jobs -> document worker -> DeepSeek
```

Инфраструктурные адаптеры вынесены из бизнес-логики:

- `src/infrastructure/config.ts` — единая конфигурация окружения;
- `src/infrastructure/session-store.ts` — Redis в production или in-memory в dev;
- `src/infrastructure/object-storage.ts` — S3/MinIO в production или локальные файлы в dev;
- `src/modules/auth/auth-service.ts` — локальный вход или OIDC/Keycloak с PKCE,
  state/nonce и проверкой JWT;
- `src/modules/processing/document-jobs.ts` и `scripts/document-worker.ts` —
  очередь и отдельный worker обработки документов;
- `src/modules/registry/repositories/` — отдельные доменные репозитории
  договоров, обязательств, задач, комментариев и дашборда;
- `src/modules/audit/audit-service.ts` — защищённый журнал действий для
  администратора;
- `src/http/http-utils.ts` — общие HTTP, JSON и multipart-утилиты.

Для production задайте `AUTH_MODE=oidc`, `REDIS_URL` и
`OBJECT_STORAGE_DRIVER=s3` в `runtime/.env`. Локальный режим предназначен
только для разработки.

## Шаг 1. Локальная PostgreSQL в Docker

Требования:

- Docker Desktop с Compose;
- свободный локальный порт `55434`.

Запуск базы:

```bash
cd "/Users/andrey/Documents/New project 2/monitoring-contract-obligations"
docker compose up -d --wait postgres
```

Проверка состояния:

```bash
docker compose ps
```

Параметры подключения для локальной разработки:

```text
postgresql://monitoring:local-development-only@127.0.0.1:55434/monitoring_obligations
```

Остановка контейнера без удаления данных:

```bash
docker compose stop
```

Удаление контейнера и тома с данными выполняется отдельно и на этом этапе не
нужно.

## Шаг 2. Первая миграция

Установить зависимости runtime:

```bash
cd "/Users/andrey/Documents/New project 2/monitoring-contract-obligations/runtime"
npm install
cp .env.example .env
```

Применить миграции и проверить таблицы:

```bash
npm run db:setup
npm run db:check
```

Статусы договора хранятся независимо:

- `status` — бизнес-статус договора: черновик, действующий,
  завершённый или архивный;
- `processing_status` — техническая обработка системой: получен, в очереди,
  обрабатывается, готов к проверке, ошибка или исключён;
- `verification_status` — ручная проверка юристом: не начата, на проверке,
  проверен или требует доработки.

Статус каждого обязательства дополнительно хранит результат верификации и
фактическое исполнение.

Для договора предусмотрено происхождение:

- `manual` — ручная загрузка;
- `kasud` — будущая загрузка из КАСУД;
- `sod` — будущая загрузка из СОД.

Поле `source_reference` предназначено для идентификатора договора во внешней
системе. Интеграции с КАСУД и СОД пока не реализуются, но модель данных к ним
готова.

Тип обязательства ограничен двумя значениями:

- `financial` — финансовое;
- `non_financial` — нефинансовое.

Фиксация исполнения хранится как в текущем состоянии обязательства, так и в
истории действий куратора. Сохраняются статус, комментарий, фактическая дата
исполнения, подтверждающий документ и причина просрочки. Для статуса
`completed` обязательны дата и подтверждающий документ; для статуса `overdue`
обязательна причина просрочки.

Проверка просроченных обязательств запускается командой:

```bash
DATABASE_URL='postgresql://monitoring:local-development-only@127.0.0.1:55434/monitoring_obligations' \
  npm run obligations:mark-overdue
```

Команда переводит просроченные обязательства в статус `overdue`, записывает
системное событие и создаёт уведомление куратору. В дальнейшем её можно
запускать по расписанию из фонового worker-сервиса.

Обработка загруженных документов выполняется отдельным worker-процессом:

```bash
DATABASE_URL='postgresql://monitoring:local-development-only@127.0.0.1:55434/monitoring_obligations' \
  npm run worker:documents
```

HTTP API только сохраняет файл и ставит документ в таблицу
`document_processing_jobs`; запрос пользователя не ждёт ответа DeepSeek.

После автоматического обнаружения обязательства получают признак
`overdue_requires_curator_input`. Он снимается после сохранения куратором
комментария и причины просрочки. Подтверждающий документ для просрочки
остаётся необязательным и может быть приложен при необходимости.

## API первого среза

Запуск:

```bash
cd "/Users/andrey/Documents/New project 2/monitoring-contract-obligations/runtime"
DATABASE_URL='postgresql://monitoring:local-development-only@127.0.0.1:55434/monitoring_obligations' npm run dev
```

По умолчанию API запускается на `http://127.0.0.1:4174`, чтобы не занимать
порт проекта «Сводика».

Откройте `http://127.0.0.1:4174/`, чтобы пройти локальный экран авторизации и
открыть личный кабинет. В dev-режиме форма создаёт локального пользователя и
сессию; пароль не сохраняется. В production маршрут `/auth/provider`
перенаправляет пользователя в Keycloak, а `/auth/callback` проверяет OIDC
токен и создаёт серверную сессию.

Доступны маршруты:

- `GET /api/health` — состояние приложения и PostgreSQL;
- `GET /api/obligations` — реестр с фильтрами, пагинацией и сортировкой;
- `GET /api/contracts/:id` — карточка договора;
- `GET /api/documents/:id/text` — извлечённый текст документа.
- `GET /api/audit-events` — журнал действий с фильтрами и пагинацией;
  доступен только администратору.

До подключения корпоративной авторизации локальный режим принимает заголовок
`X-Dev-User-Id`. Он предназначен только для разработки и не используется при
`NODE_ENV=production`.

Для реестра обязательств создано представление `obligations_registry`. Оно
объединяет обязательство, договор и исходный документ и содержит поля для
фильтрации, проверки, исполнения, риска, санкции, версии и перехода к
исходному фрагменту договора. Признак `is_overdue` рассчитывается для
отображения просроченных строк в интерфейсе.

Реестр не дублируется по ролям. Для ограничения видимости предусмотрены
организационные единицы (`business_unit`, `legal_service`, `fco`, `branch`) и
таблица `user_access_scopes`. Договор может быть связан с бизнес-единицей,
правовой службой, ФЦО и филиалом. Серверный API обязан применять эти области
видимости до выдачи строк реестра; прямой доступ к представлению без проверки
пользователя запрещён.

Для карточки договора создано представление `contract_card`. Оно возвращает
реквизиты договора и список документов с версиями, статусами обработки,
признаком актуальности, количеством страниц и наличием извлечённого текста.
Поле `storage_key` используется сервером для безопасной выдачи файла, а не
передаётся в браузер как прямой путь к хранилищу.

Для извлечения обязательств планируется использовать DeepSeek. Настройки
провайдера находятся в `runtime/.env`; шаблон переменных приведён в
`runtime/.env.example`. API-ключ не хранится в репозитории, не передаётся в
браузер и не встраивается в Docker-образ.

Проверки проекта:

```bash
npm run typecheck
npm run test:smoke
npm run test:e2e
```

Smoke-тесты проверяют здоровье API, авторизацию, дашборд, реестр и парсер
DeepSeek. Сквозной тест проверяет загрузку договора, постановку в очередь,
проверку обязательства юристом и ответ куратора.
